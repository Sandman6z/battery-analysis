# 未来大重构备忘：原生语言与性能优化候选

## 状态与适用范围

- **状态：调研备忘 / backlog，不是已批准的实施计划。** 用户要求保留本次调研，供未来大重构时考虑。
- 评估基线：仓库软件版本 v5.1.2，主分析直接读取 NDAX，独立 NDAX → XLSX 转换继续保留。
- 证据范围：源码静态检查；未进行真实 NDAX 数据的分阶段计时、峰值内存测量或跨语言原型对比。本文不承诺提速倍数，也不将候选热点称为已证实瓶颈。
- 本备忘不修改当前技术栈、不引入依赖，不替代[既有技术栈现代化路线图](2026-08-18-tech-stack-modernization-roadmap-design.md)的阶段决策。旧路线图记录的是历史基线，不能直接当作当前代码现状。

## 核心结论

**保留 Python + PyQt6 的界面、配置和业务编排，仅在性能分析证明有必要时，将少数批量数据处理热点交给 Rust/C++。不建议为了速度整体重写软件。**

先消除中间格式转换、重复扫描和重绘，再评估原生扩展。NumPy、Qt 和已有 calamine 读取路径已经利用原生实现；Python 调用代码并不意味着重活都在 Python 解释器中执行。

若确需第二种语言，优先评估 Rust 独立扩展；如果团队有 C++ 经验或可复用库，C++ 同样可行。最终选择由实测收益、维护能力和 Windows 分发成本决定，而非语言排名。

## 候选项与优先级

| 候选项 | 源码观察 | 首选动作 | 跨语言候选与边界 |
|---|---|---|---|
| NDAX 读取与分析视图整理 | `NewareNDA.read()` 后构建 Cycle/Step/Record；有分组循环和兼容旧 Excel 的混合类型表头 | 分离解析和整理耗时；保持数值类型，批量聚合，减少数据复制 | 若解析本身占主要耗时，再评估 Rust/C++ 解码热点；仅包装现有解析器不会自动加速解码 |
| 大文件 NDAX → XLSX | Record 数据在 Python 中逐行调用 `write_row()` | 分开测量读取、聚合、写入及关闭工作簿耗时和内存 | 试验 Rust `rust_xlsxwriter` 或 C `libxlsxwriter` 的合适绑定；主要改善独立转换，不等于主分析提速 |
| 图表悬停最近点查询 | 当前查看器调用线性逐点扫描；已有 KDTree 版本但未由该入口调用 | 节流、向量化查询或索引、减少重绘 | 优先利用成熟原生库，不先自行编写 Rust/C++ 查询器 |
| 多档位脉冲匹配 | 已 NumPy 向量化，但按电流/电压档位重复扫描 | 测量数据量和档位数对时间、临时数组内存的影响 | 确为热点时试验 Rust/C++ 融合扫描，保持首匹配和端点语义 |
| 容量计算与曲线过滤 | 已使用 NumPy 累积、二分定位、差分和掩码 | 保持现状，除非性能分析指出瓶颈 | 不因“当前是 Python 文件”而重写 |
| 界面、配置、规则及报告编排 | 主要为 Qt 调用和业务协调 | 保留 Python，优化实际阻塞路径 | 不建议为性能整体迁移 C++、C# 或 Rust/Tauri |

### 1. NDAX 读取及内部数据模型

相关文件：

- `src/battery_analysis/ndax/reader.py`：`read_analysis_views()`。
- `src/battery_analysis/analysis/battery_analysis.py`：单文件读取与分析、批次编排。
- `src/battery_analysis/analysis/charge_calculator.py`：数值转换、累计容量计算。

当前为了兼容旧分析接口，将文件名和文字表头作为前两行拼入分析 DataFrame，部分数值列因而变为 `object`，后续又进行数值转换。Step/Cycle 汇总还包含 Python 层逐组处理和嵌套分组。

未来可先尝试让内部模型直接保留有类型的数值列，把“Excel 表头”限制在导入兼容层和输出层；用批量聚合替代逐组取首尾值。Polars 可作为对照方案，但不预设整体替换 pandas，需要核对分组顺序、类型和转换成本。

主分析目前按文件串行处理，源码明确要求先测真实峰值内存再决定是否并行读取 NDA。并发优化与换语言是独立决策，不能为了提速无条件扩大进程数。

### 2. 大文件 XLSX 导出

相关文件：`src/battery_analysis/ndax/converter.py`。

`_build_record_sheet()` 逐行写入 Record；`convert_one()` 还包含读取、Cycle/Step 聚合和工作簿关闭。应分别测量这些阶段，不能把总耗时都归因于 Python 行循环。

原生导出原型须覆盖：

- 超过单表行数上限时的 Record 分表及重复表头。
- 电流、电压、容量精度、状态映射和时间戳格式。
- 现有读取端对导出文件的兼容性。
- 输出文件大小、压缩耗时及峰值内存，而不只比较写入循环速度。

### 3. 图表交互

相关文件：

- `src/battery_analysis/main/battery_chart_viewer.py`。
- `src/battery_analysis/main/visualization/hover_controls.py`。
- `src/battery_analysis/main/visualization/figure_builder.py`。

当前查看器接入 `_add_hover_functionality()`，查询使用 `_find_nearest_point_linear()`；同文件有 `_add_hover_functionality_kdtree()`，但不能据此认定当前入口已得到 KDTree 加速。`scipy` 未声明为项目直接依赖，也不能假定目标环境有该依赖。

优先试验查询节流、向量化或预建索引，并减少标注变化引起的整图刷新。须核对曲线显隐、过滤切换和缩放后的索引有效性，以及最近点的坐标尺度和命中语义。

只有在这些改进后，大量曲线的平移、缩放和重绘仍不达标，才重新评估 **交互查看器使用 PyQtGraph、报告图片继续使用 Matplotlib**。这会引入双绘图栈和交互迁移成本，是未来大重构的备选，不推翻既有“不迁移 PyQtGraph”的当前阶段决策。

### 4. 已向量化的计算

相关文件：

- `src/battery_analysis/analysis/pulse_matcher.py`。
- `src/battery_analysis/analysis/charge_calculator.py`。
- `src/battery_analysis/analysis/data_utils.py`。

这些模块已有 NumPy 实现。可能的进一步收益来自减少数组扫描、临时数组和格式转换，而不是把相同调用逐句翻译为另一种语言。跨语言接口应尽量整批接收数值数组，避免逐行调用和不必要的复制；最终以包含边界转换成本的总时间评价。

## 未来启动重构时的决策门槛

1. **建立真实基线**：选择小、中、大 NDAX、不同样本数及电流/电压档位数；主分析和独立转换分别测试。记录硬件、软件版本、文件大小、记录行数及冷/热运行条件。
2. **分阶段测量**：NDAX 读取、视图整理、脉冲匹配、容量计算、中间文件 I/O、绘图、报告输出分别计时；记录批次总耗时、峰值内存及交互响应延迟。不能只用一个微基准代表软件整体。
3. **先做低成本对照**：数值类型保留、批量聚合、消除重复转换、查询索引和节流。以优化后的 Python/原生库组合为比较基准。
4. **只做一个热点原型**：按耗时占比和用户痛点选择模块，对照原实现验证吞吐量、内存、结果和分发成本。
5. **收益达标再集成**：实施前确定可接受的端到端收益和维护预算；原型未达标则保留现状，不为引入新语言而引入新语言。

按 Amdahl 定律，若某模块占原总耗时的比例为 p，模块加速 s 倍，则整体加速约为 `1 / ((1 - p) + p / s)`。例如占比 10% 的模块加速 10 倍，整体仅约 1.10 倍。

## 正确性与交付约束

- 保持配方电流档位、单位、取整、首匹配脉冲、端点、累计容量、缺失值和异常分类语义；不得用 0 填充缺失数据来换取便利。
- 建立新旧实现的差分回归；仅浮点计算误差可使用经明确批准的容差，不能放宽业务阈值来让测试通过。
- 报告路径须验证现有 Excel/Word/CSV/JSON/PNG/SVG 消费端和判定结果，不能以计算变快为由牺牲报告一致性。
- 对 Rust/C++ 扩展验证项目 Python 3.14、Windows、PyInstaller 打包和目标机器上的加载；记录构建工具链、依赖许可、发布和维护成本。
- 批量并发仍需遵循现有 CPU 留核策略并单独验证内存预算，不能将 worker 数预算误当成 CPU 利用率硬限制。
